The architectural decisions

Build a small Maestro workflow runtime around the existing execution seams. Use Python’s standard library, SQLite, Git, TMUX and the existing adapter protocol. Make configured agent roles first-class workflow nodes. Adopt bounded planning and local graph repair; reject a general agent framework or a universal graph database.

kind is one of agent, function, tool, human, wait, decision, join. A project executable or existing adapter is a tool; an internal pure transformation is a function. Decisions use registered pure predicates over typed outcomes. A human node represents an interaction in the engineering graph and enters a durable wait; it is not simulated by an AI agent.

Edges bind named artifact ports and express requires with an optional named outcome guard. Provenance relations such as produces, verifies, supersedes and derived_from are not scheduling edges. Do not make quota_low or retry arbitrary backward graph edges.

States and required invariants

Task run phase: planned → active → accepted, with waiting, blocked and canceled alternatives. Node phase: pending → ready → claimed → running → succeeded; alternatives are waiting, failed, skipped, canceled and uncertain. Attempts are append-only outcomes; a retry creates a new attempt and returns the logical node to readiness through a checked transition. Artifact/task validity is separately current | stale | unknown, so later invalidation does not rewrite an earlier acceptance event.

  • Only a ready, authorized node with current inputs can claim resources. Claim, lease epoch and dispatch intent commit together before a process starts.
  • At most one writer owns a worktree; at most one integration operation owns the target branch. Lease expiry alone does not prove an old writer has stopped, and neither does a clean launcher exit: a launcher was measured returning 0 while its detached child was still alive, after which the lock was granted to a replacement. The lease binds to the process that writes, not to the process that started it, and ownership is released only on positive proof of exit. (amended 2026-09-08.)
  • Every reachable accepting path includes all required verification and effect outcomes. An optional skipped node has a recorded predicate/reason; it cannot satisfy a required check.
  • An AND join requires all activated required branches. A candidate selection join accepts exactly one eligible winner and binds that winner’s artifacts; it cannot mix patches or proofs from different candidates.
  • Every model call uses a persisted AgentBinding. A routing failure is a typed wait/block, never silent fallback to an unnamed model or an unapproved billing category.
  • Every acceptance record identifies the verified source snapshot, policy, required evidence and any explicit exemption. Required checks cannot be erased by a planner, reviewer or generated template.
  • Graph revisions, human decisions, execution attempts and superseded tasks remain traceable. A restart, backend switch or revision cannot reset the logical task’s retry/repair counters.

Database and filesystem ownership

Use .orchestrator/control.sqlite3 in WAL mode with foreign keys, bounded busy handling and full synchronous durability on a local filesystem. Persist commands, events, task/spec revisions, workflow revisions, node/attempt projections, leases, waits, effect receipts, artifact references, verification dependencies and snapshot metadata. Index ready states, unresolved effects, lease owners and task/event sequence. Use ordinary adjacency tables and Python graphlib/DFS for first-version graph operations.

The controller is the sole domain-state writer. CLI/Telegram clients enqueue idempotent commands; launched workers write attempt-scoped result envelopes. The controller validates and ingests them. The watchdog checks controller identity and enqueues reconciliation requests rather than racing to edit task state. An independent HALT sentinel remains an immediate stop input and is never cleared by initialization or recovery.

Store artifact bodies outside SQL by content hash. Write a temporary file, flush it, atomically rename and flush its directory before committing its reference. Orphan artifacts are collectible; a referenced missing artifact blocks its consumers. Keep large logs and optional raw transcripts out of reducers. State and journal compatibility exports carry their last projected event sequence and are read-only projections after cutover.

Project policy becomes a task execution graph

Adopt the project-specific construction hypothesis with a narrower authority boundary. A repository has stable engineering practice, but no static graph can anticipate every roadmap discovery. Save facts and reusable policy once; compile and revise concrete workflows as work is discovered.

What changes in maestro init

  1. Discover without executing project code. Read tracked manifests, CI definitions, test/build configuration, package boundaries, documented commands, configured adapters, main-branch evidence and existing project rules. Record each fact’s source path, hash and confidence. Do not infer the target branch from the currently checked-out feature branch when an explicit setting or local remote-HEAD reference exists. Mark ambiguous commands as unresolved.
  2. Construct a reproducible policy. Select built-in templates for ordinary change, deterministic script, manual preparation/action, asynchronous job and resumable work. Generate workflows/project.yaml plus role/profile references; configure actual test/build adapters from verified facts. Retain the current project/core seam and non-clobbering .new behavior. Store transient detection details in .orchestrator/project-profile.json; commit stable choices and their source fingerprints in policy.
  3. Record what could not be resolved. Detection is deliberately sound and incomplete — across eight policy fixtures it produced zero false requirements and three structural misses (nested monorepo test suites, generated assets, service dependencies). That asymmetry is the right one, but silence is not. When init meets a structure it cannot resolve it emits an explicit unresolved[] fact with its source path, and an unresolved policy fact fails closed: the compiler requires the full suite and refuses affected-check skipping for anything it touches. A visible unknown, never a silent miss. For the same reason, setup reports a scaffold outcome and a host-dependent loop verification as two results, never aggregated into one exit code. (amended 2026-09-08.)
  4. Fill only consequential gaps. An optional setup adviser reads facts and existing project instructions, proposes project-specific roles/checks and emits a typed policy patch. If choices change permissions, quality gates, paid usage, external actions or architectural scope, present one combined diff/decision to the operator. Existing authorization is reusable; safe deterministic scaffolding and factual refresh do not require another approval. An ambiguous required test or deployment contract blocks only the dependent lane.
  5. Validate and rehearse separately. Compile representative task fixtures under paid and free policies using available capability fixtures, validate all accepting paths, and rehearse in a scratch repository with inert adapters/backends. Never call the live project loop or reset its halt/pause flags as an init test. `doctor` distinguishes configured, statically valid, exercised and unavailable capabilities.

Detection refreshes automatically when its source hashes change. Behavioral policy changes are versioned proposals; only changes inside the already approved envelope activate automatically. Explicit policy edits or a new acceptance contract produce a new applied version. Running workflows remain pinned unless a safety change requires pause/invalidation. This resolves the earlier plan’s “approve every synthesized workflow” proposal into a narrower, practical rule.

Compile mechanically; ask an agent only for a planning result

The compiler consumes the applied task spec, project policy/profile, base revision, valid prerequisite outputs, risk facts, execution objective and capability catalog. It normalizes the lane, computes required outcomes, chooses a template, inserts deterministic preparation/verification/effect nodes, conditionally inserts agent roles, binds artifact ports and validates the complete graph. The library is templates and named versioned fragments, not five monoliths: a fragment declares its input/output ports, the obligations it discharges and its activation predicate, and a template is a composition of fragments. Otherwise adding one conditional reviewer means editing built-in templates — the same coupling that makes the present orchestrator hard to extend, one abstraction level up. The compiler’s invariant is the minimal shape that discharges the required outcomes. Every optional node carries a recorded activation reason and is treated as a hypothesis under measurement, never as a default; a trivial documentation task compiles to a single agent node, and a fixture asserts it. Template and fragment selection is deterministic — a function of task class, risk and policy. A planner may propose a different template or fragment set as a typed proposal the compiler validates, but it never selects: template choice determines which acceptance obligations apply, so a planner choosing its own template is a planner choosing its own gate. (amended 2026-09-08.) It returns an immutable revision and a human-readable explanation of every included/omitted optional node.

Classification starts with explicit task metadata and deterministic indicators: scope, dependency count, public contracts, migrations, security-sensitive areas, service effects and required modalities. A missing classification defaults conservatively. A planner is invoked only when requirements or decomposition require reasoning; its output is PlanProposal, not executable authority. The deterministic compiler checks the proposal against policy. Risk can rise after the diff exposes more scope; lowering an established risk requirement needs evidence and the appropriate policy authority.

For a precise bug fix, paid mode can compile prepare → implement → verify → integrate → accept, with no planner or generic reviewer. A schema migration may require a planner, migration/compatibility checks, a reviewer and a human deployment decision. A UI change can require a visual review role only if its backend has image/browser capabilities. A script task can contain zero AI nodes. Missing tests create a concrete verification-work prerequisite or test-design node; they do not create a “test passed” exemption.

Roadmap intent, imports and mutation

Keep Markdown YAML blocks as the authoring surface and preserve the free prose around them. One strict parser returns errors with task/block locations for malformed YAML, duplicate IDs, missing prerequisites, cycles, invalid dispatch shapes or missing acceptance requirements. Parse the completed-task archive as historical input. Import legacy completions as legacy_accepted with their original provenance level: they can satisfy migrated roadmap prerequisites, but cannot manufacture fresh verification evidence or cache entries.

maestro roadmap apply validates and applies a complete definition snapshot using an expected graph revision and source hash. Runtime authority is the applied SQL revision; editing a Markdown file is a proposal until applied. Dispatch checks for authoring-file drift and pauses affected new claims until import is resolved. Safe, already authorized changes may be imported automatically; ambiguous or scope-changing ones await a decision.

Maestro-generated mutations use the same command boundary: add_task, add_dependency, split_task, supersede_task, invalidate_inputs and select_alternative. A split leaves the parent as a group; its original prerequisites gate all entry children, and required exit children collectively satisfy its downstream obligation. No task is physically deleted to simplify history.

A successful mutation transaction records its cause and new revision, then a durable outbox renders the corresponding authoring/export change using compare-and-swap against the known document hash. If a human edited the file meanwhile, keep both versions, flag a conflict and block affected dispatch; never overwrite the human edit. Unrelated running work can continue on its pinned revision. Completion/UPCOMING/dependency-map generation becomes projection work rather than another independent source of task truth.

An agent node is a configured responsibility

An AgentDefinition is a reusable, versioned role contract. It includes responsibility and exclusions, instruction/system-profile content, input and output schemas, context assembly rules, exact skill references and hashes, logical tools, permission requirements, permitted backend capabilities, model specializations, effort policy, success/failure conditions, memory/handoff policy and observability requirements. A node instantiates this definition with task-specific inputs; the router binds it to a runtime, model and effort.

Instructions are layered explicitly: Maestro’s execution contract, applied project rules, role instructions, task inputs and evidence. Record how the backend receives each layer. If it only accepts an appended profile, do not report full system-prompt replacement. Resolve skill content before dispatch and include only relevant authorized skills; a missing required skill is a configuration failure. Do not install skills or expose new tools during an unreviewed run.

Portable outputs and instructions

Use a versioned NodeResult envelope with node/attempt ID, input hash, source snapshot, output artifacts, claims, findings, unresolved requirements and proposed mutations. Parse and validate required keys, enums and criterion coverage deterministically. Incomplete or malformed results are not success. Permit one bounded format-repair request where useful, charged to the node’s attempt budget; retain the original and repaired output.

Never share an accumulating conversation across the graph. Pass artifact references and targeted evidence between nodes. A reviewer has a distinct session and read context even when it uses the implementer’s backend and model. The same AgentDefinition can run through a subscription CLI or a free model harness without vendor names leaking into the task schema.

Shared mechanisms, different optimization objectives

Paid-agent mode: maximize useful, verified engineering outcomes per constrained subscription budget. A stronger early planner or reviewer is worthwhile when it avoids more expensive failure and rework. “Smallest sufficient graph” applies to AI calls, not to the number of reliable deterministic checks.

Free-model mode: maximize task success and final quality. Token counts and prompt length have no cost term. Additional inference, context, candidates and independent checks are welcome when they improve outcomes. Physical context limits, attention quality, available hardware, time and operator interruption still constrain execution; they are not disguised token budgets.

Initial presets are operational starting points, not research-proven optima. Paid mode allows one implementation repair before a targeted diagnosis/escalation decision. Free mode starts with up to three repair rounds and at most four candidates per wave, with another wave permitted when evidence supports a distinct strategy. A repeated identical failure without new evidence on two consecutive rounds triggers diagnosis or a human block; changing backend alone is not progress. Users can enlarge these quality/time/hardware envelopes. No free-mode stop is triggered by cumulative tokens.

For both modes, every round’s tests, criteria coverage, findings and disposition determine whether another round is useful. A deadline or resource envelope that prevents completion yields blocked/incomplete with the best artifacts preserved, not “success by majority.” A fully deterministic task does not acquire agents merely because the mode is free.

Hybrid is a resource policy, not a third architecture

Separate objective = paid_efficiency | free_quality from allowed_billing = subscription | no_marginal_charge. Hybrid enables both billing categories with an explicit paid allowance and reservation policy. Each backend instance declares its billing model; no vendor is intrinsically “paid” or “free.” A free runtime’s service limits remain capacity constraints even if they are not monetary costs.

A useful hybrid graph could use a strong subscription planner to resolve a difficult contract, free implementer candidates, free independent test design, and a subscription reviewer only for an unresolved high-risk finding. Alternatively, a capable subscription implementer may outperform many free attempts and be the efficient choice. Route by measured strengths and task risk; do not impose “cheap work first, paid escalation last” when that causes more rework.

Reserve scarce paid capacity for nodes with the largest quality improvement or failure-reduction benefit relative to expected subscription usage. Free nodes cannot consume that reserve. Switching objective for future work changes graph compilation; changing it during a run produces a policy/revision event and recompiles only unfinished work. Valid artifacts survive the switch; additional free-mode obligations are added before acceptance. Paid usage eligibility is never silently enabled by a mode change.

Branches, joins and local repair

For conditional review, a policy decision emits an outcome such as review_required or review_not_required; the inactive path is explicitly skipped. For AND work, independent checks/readers may run in parallel over an immutable snapshot. Tests that write into the source tree require a separate snapshot or an exclusive mutation lease, even if they are called “verification.”

Candidate groups fan out from the same task/base/acceptance contract. Each candidate is independently verified against the same trusted requirements. Selection first removes ineligible candidates: failed required check, stale evidence, unresolved blocking finding, unauthorized change or missing output. Among eligible candidates, deterministic criteria rank requirements coverage, reproducible defects, compatibility, maintainability signals and project preferences; a reviewer resolves judgment-dependent differences when useful. Stable candidate ID breaks a true tie. Passing votes and self-reported confidence never overrule a failing test.

If two candidates contain useful parts, combining them creates a new candidate with both as provenance parents. It must pass the full relevant gate; neither parent’s acceptance transfers to the combination. Unselected branches are canceled only after active processes stop, and their patches/results are retained for the run’s retention period.

A discovery becomes a GraphPatchProposal with expected revision, triggering evidence, affected nodes, new prerequisites/outputs and reason. The controller validates it against policy and commits the mutation transactionally. Running consumers of invalidated inputs lose eligibility to merge; checkpoint and stop them at a safe boundary when their work is no longer useful.

Adding a prerequisite to an active task cannot retroactively make an invalid execution valid. Pause the affected task, preserve its partial work, apply the new DAG and resume through a new revision. The controlled-operation protocol

  1. Validate the node, inputs, permissions and resource availability. In one SQL transaction, record the attempt, claim with fencing epoch and operation intent.
  2. Dispatch outside the transaction with a stable effect_key = hash(project, logical_operation_id, input_hash, target_scope). Retries of the same effect retain the key; changed inputs or an intentional new operation get a new key.
  3. The launcher records process identity/boot identity/start time, workspace, command/spec hash, native handle if available, and acknowledgment. A heartbeat signals liveness; it is not evidence of engineering progress.
  4. Write output/receipt artifacts durably, then transactionally append the completion observation and update projections. Only the current lease epoch may commit a node outcome.
  5. On any gap between these stages, probe the recorded operation and physical state. Reuse a durable result, adopt a surviving process, perform a safe retry, or mark it uncertain.

Use unique command IDs and expected aggregate revisions to make duplicate deliveries and stale updates harmless. Append event and projection changes in the same database transaction. A projection rebuild replays recorded domain events; it never calls a model, executes a shell command, sends a message or re-applies Git effects. Event schema changes have explicit versioned reducers/upcasters and migration tests.

Scheduling, operator control and self-update

Two ready frontiers, one resource discipline

Roadmap readiness means prerequisites and assumptions are current and policy permits the task. Workflow readiness means its activated input producers have completed. Resource admission is a separate decision. This prevents a full agent pool from hiding a ready deterministic job or turning an unavailable model into a fake dependency edge.

Start with an explainable greedy scheduler: operator priority, overdue/aging work, downstream blocked work, fit to available resources, and predicted conflict. Use estimates only when recorded; do not pretend descendant count is a measured critical-path duration. Distinguish worktree writer slots, read/test CPU and RAM, GPU/VRAM, backend session limits, subscription usage pools, exclusive project resources and the target integration lock. Preserve existing parked/cooldown/hold filters.

Per-project subscriptions and multiple backend aliases can share one account pool; model aliases do not create new quota. Actual account usage includes human/other-project consumption. For multiple concurrent Maestro projects on one host, add a small host admission ledger keyed by pool ID in P8; reservations are leased and reconciled with known process ownership, not optimistic token arithmetic. It is coordination metadata, never a second task database. Do not assume host-local admission coordinates remote machines or the operator’s own sessions.

Use predicted source/component overlap to defer likely conflicting writes in different worktrees, but do not turn a heuristic conflict into permanent roadmap ordering. Explicit project resource labels remain the reliable exclusion mechanism. Free candidates may compete for a GPU or a limited local serving slot; schedule them serially when necessary. Human waits consume neither inference nor CPU slots, although a running external job keeps its actual resource lease.

HEFT, work stealing, CP-SAT and learned schedulers are deferred until duration/resource/conflict measurements justify them. Small adjacency tables and deterministic ranking suffice for the present local scale. Remote workers and distributed graph storage are outside this implementation.

This is not hypothetical: the Claude sampler carry-forward merges window values when a render lacks them and stamps the result with the write time, so two samples can carry one underlying reading. An unchanged underlying reading across a pair is “no new observation”, never a zero delta — a manufactured zero reads as “this task consumed nothing”, which is worse than a gap. Token/context accounting and subscription-allowance accounting stay separate, non-convertible quantities, and a CLI’s reported USD figure is a list-price estimate, not evidence of a subscription charge. A delta is attributable only under a stated isolation contract: a fresh observation at both ends, an unchanged reset epoch across the pair, a non-negative delta, and no other session known to be on that pool. Run a zero-work control — the probe sequence with no task — so the measurement layer’s own apparent cost is known before any route is compared against another. (amended 2026-09-08.)

Key pools by (account, pool) and compute reserves per pool; “one account, one pool” is not a safe assumption. Measured, not assumed: one installed backend exposes four pools on a single account whose windows diverge sharply — a third-party weekly pool at 27% remaining beside a model-family weekly pool at 90%. A single per-account headroom number would have been actively wrong. (amended 2026-09-08.)
  • Allowance-efficiency statistics (shared with E1). Per route, within one matched task class: 5-hour percentage points per verified task, weekly percentage points per verified task, verified tasks per 100% of the 5-hour allowance, and verified tasks per 100% of the weekly allowance. Failed attempts and rework contribute their consumption to the numerator. A route that consumed allowance and verified nothing records 0 verified-per-100%, not a blank.

What is explicitly not being implemented

No wholesale LangGraph/CrewAI/AutoGen/SDK migration; no Temporal/DBOS/Restate server in the initial release; no universal ontology or Neo4j/Memgraph requirement; no LLM-extracted GraphRAG source index; no automatic embeddings or vector service; no always-on Joern; no unrestricted graph-rewrite/plugin DSL; no agent-to-agent group chat bus; no default standing architect/planner/tester/reviewer/documenter chain; no automatic paid API fallback.

Do not implement full MCTS/Graph-of-Thought roadmap search now. The reason in free mode is unresolved reward validity, correlated evaluation and orchestration value—not tokens. Bounded explicit alternatives already capture the useful part. Reconsider deeper search only through a targeted quality experiment. Do not add distributed workers, a multi-user control plane, cloud dashboards or a React Flow/ELK application before the local workflow needs exceed static exports and simple views.

Do not restrict graph work to retrieval or durability alone. The proposed runtime must actually execute project-specific engineering graphs with distinct role definitions and support the different paid/free policies. Conversely, do not block useful workflow and evidence work on implementing a complete semantic code index.
