# Maestro M2: Backend Drivers & Mid-Work Switching — Implementation Plan

> **Read `docs/EXECUTION.md` first.** It is the process source of truth and wins over this document on
> any process question. This file is the **task detail for stage M2**, written at the start of the
> stage as EXECUTION.md requires. Design authority is `docs/DESIGN.md` §6–§7.
>
> Steps use checkbox (`- [ ]`) syntax. Under workflow execution, fan-out agents create and edit only
> their own listed files and run **no git commands**; the orchestrating session commits per batch.

**Goal:** Put both Claude and Codex behind one `AgentBackend` protocol, selected per role, and make a
running implementer switchable mid-task from one backend to the other with its uncommitted work
intact.

**Architecture:** A driver owns exactly three things — *build the launch invocation*, *interpret the
exit*, *report usage*. Everything else (worktree lifecycle, tmux window naming, sentinel protocol,
brief construction, state and journal) stays in the M1 modules unchanged. Core code branches on
**capabilities, never on backend name**; that rule is enforced by the shared protocol suite, which
runs the same test bodies against both drivers and gates the optional cases on a declared capability.

**Tech Stack:** Python 3.11, pytest 9. No new runtime dependencies — `pyyaml`, `python-dotenv`,
`requests` only. The Codex integration shells out to the `codex` CLI; it does not use the Codex SDK.

## Research findings this plan is built on

M2's research fan-out ran on 2026-08-12 (4 agents, 403K tokens, workflow `wf_a93306d7-f93`). Every
statement below was **verified against the tooling installed on this machine**, not recalled. Two of
them contradict `docs/DESIGN.md` §6 as written — see "Design corrections" below. **Do not re-derive

### F1 — `codex exec` has a real, documented resume handle → `native_resume = True`

This resolves the M2 open question in `docs/DESIGN.md` §13 and `docs/PROGRESS.md`. **The Codex driver
declares `native_resume = True` and does not always re-brief.**

- Installed: `codex-cli 0.147.0` at `/home/dan/.local/bin/codex` (symlink into
  `@openai/codex/bin/codex.js`).
- The handle is the **`thread_id`** on the first JSONL event of any `codex exec --json` run:
  `{"type":"thread.started","thread_id":"019ff499-deaf-77d1-acd4-e2135c856fa8"}`.
- It is a **public, documented contract**, not an internal detail. The official
  `@openai/codex-sdk` TypeScript source documents it verbatim: *"The identifier of the new thread.
  Can be used to resume the thread later."* (`sdk/typescript/src/events.ts:6-10`).
- Resume command: `codex exec resume <SESSION_ID> [PROMPT]`. Verified end to end on this machine —
  the same `thread_id` came back and history was replayed (`input_tokens` grew 19050 → 44304 → 70172
  across three turns of one thread).
- Sessions persist as `~/.codex/sessions/YYYY/MM/DD/rollout-<ISO8601>-<thread_id>.jsonl`; the UUID in
  the filename **is** the `thread_id`. Resuming **appends** to the same file.

Three gotchas that the driver must encode, all verified:

| # | Gotcha | Consequence for the driver |
|---|---|---|
| G1 | `codex exec resume` accepts **none** of `-s/--sandbox`, `-C/--cd`, `--add-dir`, `-p/--profile`. Those must be placed **before** the `resume` subcommand — and they then do take effect (the rollout's `turn_context` recorded the new `cwd` and `sandbox_policy`). | Argv order is `codex exec <exec-flags…> resume <thread_id> <prompt>`, never `codex exec resume <thread_id> <exec-flags…>`. |
| G2 | `codex exec resume --last` **hangs** with no output for 150 s+ (killed at exit 124, 16.8 s user / 12.9 s sys) from a cwd with no matching session — it appears to scan all 17,794 rollout files. | **Never use `--last` in automation.** Always resume by explicit `thread_id`. |
| G3 | A bogus thread id fails fast and free: exit 1, `no rollout found for thread id … (code -32600)`, no model call, no quota spent. | Safe to attempt a resume speculatively; treat exit 1 + that message as "handle is dead, re-brief fresh". |

Also: there is a **second, older `codex` on PATH** — `/usr/bin/codex` is `codex-cli 0.122.0`.
`~/.local/bin` precedes `/usr/bin` today so 0.147.0 wins, but a PATH change would silently swap
versions. **The driver resolves and records the absolute binary path and its `--version` once, and
`doctor` reports both.**

### F3 — Codex usage telemetry: DESIGN.md §6's mechanism is wrong, its conclusion survives

**REFUTED as written:** `context-used`, `five-hour-limit` and `weekly-limit` are **not emitted** by
Codex. They are internal **TUI status-line item identifiers** (a Rust enum,
`tui/src/bottom_pane/status_line_setup.rs:103-116`), rendered only inside the interactive TUI. There
is no external status-line command, no JSON payload, no file, and **no status-line hook** — Codex's
hook system has 11 events (`PreToolUse … Stop`) and none fires on a status-line render, so the
Claude sampler pattern **cannot** be ported. There is no `codex usage` / `codex limits` subcommand,
and `codex exec --json` carries only per-turn token counts (`TurnCompletedEvent.usage`), no
rate-limit windows.

**But usage telemetry is still achievable, by two other verified routes:**

- **Source A (primary — passive, per-turn, zero extra network calls): the rollout JSONL.** Every
  Codex session, `codex exec` included, appends `token_count` event records to its rollout file
  carrying **both** the context figures and the full rate-limit snapshot:
  `{"type":"event_msg","payload":{"type":"token_count","info":{"total_token_usage":{…,"total_tokens":2023580},"model_context_window":258400},"rate_limits":{"limit_id":"codex","primary":{"used_percent":98,"window_minutes":10080,"resets_at":1787036664},"secondary":null,…}}}`.
  Confirmed present on an `originator: codex_exec` rollout, not just TUI ones. Locate the file from
  the `thread_id` captured at launch.
- **Source B (fallback, when no run is active): `codex app-server`.** It speaks line-delimited
  JSON-RPC on stdio and answers `account/rateLimits/read` with
  `{"rateLimits":{"primary":{"usedPercent":98,"windowDurationMins":10080,"resetsAt":1787036664},"secondary":null,"planType":"plus",…}}`. No model tokens consumed.
  **Gotcha G4:** stdin must be **held open** (a FIFO) until the reply arrives. On EOF the server tears
  down the stdout writer before flushing and exits **0 with zero bytes** — a silent no-answer that
  looks exactly like "the feature does not exist".

Two more findings that change the design of the threshold logic:

- **G5 — there is no five-hour window on this account.** Every rate-limit record sampled has
  `window_minutes: 10080` (weekly) and `secondary: null`. `five-hour-limit` in the TUI really means
  "the primary window, whatever its duration"; the label is derived from `window_minutes` at render
  time (`tui/src/chatwidget/rate_limits.rs:77-102`). **Therefore: map windows by `window_minutes`,
  never by field name.** A driver that assumes `primary == 5h` will let a threshold that can never
  fire silently disable switching.
- **G6 — `context_used_pct` must be computed, not read**, and naively it is wrong:
  `total_token_usage.total_tokens` is **cumulative across the session** and routinely exceeds
  `model_context_window` (2,023,580 vs 258,400 in the sample). Codex's own helper also subtracts a
  `BASELINE_TOKENS = 12000` allowance. The exact TUI percentage formula was **not** traced —
  see Open Questions. Treat Codex `context_used_pct` as **best-effort, nullable**.

Side finding, not maestro's problem but worth the operator knowing: `~/.codex/config.toml:74` lists
status-line items `weekly-used` and `weekly-reset` that the **installed** 0.147.0 does not know (they
exist only in the newer source checkout at `/home/dan/projects/codex-statusline`).

### F4 — the Claude side, exactly as the reference does it

`docs/DESIGN.md` §6's flag list is also wrong. **The reference builds no `--strict-mcp-config`,
`--mcp-config`, `--add-dir`, `--dangerously-skip-permissions` or `--output-format` anywhere.** The
real argv, in this order, brief positional and **last**:

```
claude -p --model <model_id> --session-id <uuid4> [--system-prompt-file <abs path>] <brief>
```

- `--system-prompt-file` is emitted **only when that file exists**.
- **`--resume <uuid>` replaces `--session-id`; the two never appear together**, and the resumed run
  must have `cwd` = the original worktree.
- The launch is **indirect**. `launch_implementer` writes three files into `workspace` —
  `brief.txt`, `session_uuid.txt`, and a generated `launch.py` (chmod 0o755) that contains the argv —
  then runs it in a new tmux window: `tmux new-window -t <session> -n agents:impl-<task_id>
  'cd <worktree> && <venv python> <launch.py>'`. `impl.log` is written by the generated launcher, not
  by `launch_implementer`.
- **stderr is merged into stdout** (`stderr=subprocess.STDOUT`) into `<workspace>/impl.log`. M2 must
  merge them too: all five captured exhaustion samples are therefore stream-agnostic and it is
  **undetermined** whether Claude emits the notice on stderr.
- **The reference has no exit-code mapping for implementers.** The return code is discarded; outcome
  is determined by tmux-window liveness plus the `PAUSED` / `DONE` / `FAILED` sentinel files, checked
  in that order. `ExitVerdict` is therefore *new surface* in M2, not an extraction — see Task 2.
- **Quota detection and reset parsing already live in `maestro/quota.py`, byte-identical to the
  reference.** Reuse them; do not re-derive. `_LIMIT_RE` matches
  `hit your/the (usage) limit | usage limit reached | rate-limit | too many requests |
  overloaded_error`; `_resolve_limit_reset(tail)` is a 3-tier resolution — a **future**
  `usage.json five_hour.resets_at` → a prose regex over the message → `now + 1h` — always returning
  Zulu ISO, over a **25-line tail window**, merged into `paused_until` by string comparison.
- Claude usage sampling is a **first-class Claude Code extension point Codex has no equivalent of**:
  `settings.json` `statusLine` runs `~/.claude/statusline-command.sh`, which receives model, context
  window and rate limits as JSON on stdin and writes `.orchestrator/usage.json` **atomically**
  (temp + `mv`), **only** for repos that already have a `.orchestrator/` directory, with a
  carry-forward merge so a render from a parallel session lacking `.rate_limits` cannot erase good
  values. Exact shape (one line):

```json
{"context_used_pct":null,"context_total_input_tokens":0,
 "five_hour":{"used_pct":95,"resets_at":1786373400},
 "seven_day":{"used_pct":91,"resets_at":1786453200},
 "model":"Sonnet 5","updated_at":"2026-08-10T10:36:59Z"}
```

`resets_at` are unix epoch seconds; `used_pct` are integers; `updated_at` is UTC ISO-8601 Z.
**This is the normalisation target for both drivers.**

## Design corrections

Two factual premises in `docs/DESIGN.md` §6 are wrong. **The §2 decisions are untouched** — D1
(pluggable drivers) and D2/D3 (switching, checkpoint handoff into the same worktree) all survive
intact; only the descriptions of *how the tools behave* were mistaken.

- [ ] **C1.** §6 "claude driver — wraps the proven invocation: `claude -p --model
  --system-prompt-file --strict-mcp-config --mcp-config --add-dir --resume <uuid>`". Four of those
  seven flags appear **nowhere** in the reference. Correct to the F4 argv.
- [ ] **C2.** §6 "Codex's statusline already emits `context-used`, `five-hour-limit` and
  `weekly-limit`, so usage telemetry is at parity". The mechanism does not exist (F3). Parity is
  still reachable, via the rollout JSONL and `app-server`. Correct the mechanism, keep the
  conclusion, and add the `window_minutes` warning (G5).

Both are recorded as an appended "**Correction (M2 research, 2026-08-12)**" note in §6 rather than a
silent rewrite, so the original claim and its refutation stay visible.

  stay green**, with the single expected exception of `test_launch_implementer_agent_argv`, which is

- **Capabilities, never names.** No `if backend.name == "codex"` anywhere in `maestro/`, and no test

- **No new runtime dependencies.** `pyyaml`, `python-dotenv`, `requests` only. Codex is reached by
  shelling out to its CLI, never via the SDK.
- **No test may spend quota or reach a network.** Every `subprocess.run` against `claude` or `codex`
  is monkeypatched. A test that actually launches an agent is a defect. The *only* sanctioned live
  invocations are the two capability probes in Task 8's acceptance, run by the orchestrating session,
  not by the suite.
- **Judge call sites are out of scope.** `gates.py:117`, `selfheal/diagnose.py:62` and `merge.py:147`
  keep their hardcoded `claude` invocation in M2. Backend-dispatching them is M3 work (they are
  really model-selection, not session-lifecycle, concerns). Recorded here so the decision is explicit
  rather than an oversight.
- **`maestro/backends/` is new code with new tests** under `tests/backends/`, not
  `tests/characterization/`. There is no legacy counterpart to characterise.
- Design source of truth: `docs/DESIGN.md` §6–§7. Process: `docs/EXECUTION.md`.

## Task 1: `backends/base.py` — the protocol

**Files:** create `maestro/backends/__init__.py`, `maestro/backends/base.py`.

- [ ] **Step 1.** Define the value types. Use `NamedTuple`/`dataclass`, no third-party validation.

```python
class Capabilities(NamedTuple):
    native_resume: bool         # can resume a session by a stable id
    system_prompt_file: bool    # supports full-replace lean profiles
    usage_telemetry: bool       # can report live context% / quota%
    sandbox: bool               # can constrain filesystem/network access

@dataclass(frozen=True)
class LaunchSpec:
    task_id: str; session_id: str; model: str; brief: str
    workspace: Path; worktree: Path
    system_prompt_file: Path | None = None
    sandbox: str | None = None

@dataclass(frozen=True)
class Handle:
    backend: str; session_id: str; native_id: str | None; workspace: Path; window: str

@dataclass(frozen=True)
class ExitVerdict:
    kind: Literal["ok", "quota_exhausted", "crashed"]
    reset_at: str | None = None      # Zulu ISO, only for quota_exhausted
    evidence: str = ""

@dataclass(frozen=True)
class Usage:
    context_used_pct: float | None
    windows: dict[int, WindowUsage]   # keyed by window_minutes  (G5)
    model: str | None
    updated_at: str
```

  **Design note, from G5:** `Usage.windows` is keyed by **`window_minutes`**, not by the names
  `five_hour`/`seven_day`. Named accessors (`.five_hour`, `.seven_day`) are convenience lookups for
  `300` and `10080` that return `None` when absent. This is what stops a threshold that can never
  fire from silently disabling switching on an account with no 5-hour window.

- [ ] **Step 2.** Define `AgentBackend` as a `typing.Protocol` with `name`, `capabilities()`,
      `launch(spec) -> Handle`, `resume(handle, prompt) -> Handle`, `parse_exit(rc, log_tail) -> ExitVerdict`,
      `usage() -> Usage | None`, exactly as `docs/DESIGN.md` §6 specifies.
- [ ] **Step 3.** Provide `to_usage_json(usage) -> dict` / `from_usage_json(dict) -> Usage`
      normalising to the **F4 shape** so both drivers and the existing `quota.py` reader agree.
- [ ] **Verify:** `python3 -m pytest tests/backends/test_protocol.py -k base`

## Task 2: `backends/claude.py` — parity with the reference

**Files:** create `maestro/backends/claude.py`, `tests/backends/test_claude_driver.py`.

- [ ] **Step 1.** `launch()` builds **exactly** the F4 argv: `claude -p --model <id>
      --session-id <uuid4> [--system-prompt-file <abs>] <brief>`, brief positional and last,
      `--system-prompt-file` only when the file exists, and **no other flags**. Merge stderr into
      stdout. Return a `Handle` whose `native_id` is the uuid, and persist it to
      `session_uuid.txt` as today.
- [ ] **Step 2.** `resume()` emits `--resume <uuid>` **in place of** `--session-id`, never alongside,
      with `cwd` = the original worktree.
- [ ] **Step 3.** `parse_exit()` **delegates to `maestro.quota`** — `_LIMIT_RE` over the **25-line**
      tail, then `_resolve_limit_reset` for the reset. Do not re-derive either. Return
      `quota_exhausted(reset_at)` on a match. **Note honestly in the docstring** that the reference
      has *no* exit-code mapping (outcome is window liveness + sentinels), so `ok`/`crashed` is new
      surface: map `rc == 0 → ok`, non-zero without a limit match → `crashed`, and leave the
      sentinel/liveness protocol in `orchestrator.py` untouched as the authority.
- [ ] **Step 4.** `usage()` reads `.orchestrator/usage.json` (F4 shape) and maps
      `five_hour → windows[300]`, `seven_day → windows[10080]`. `capabilities()` returns
