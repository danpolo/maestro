03

The modules that should change

Control

Typed event and projection module

Versioned event envelope, causation/correlation, artifact references, compatibility exports, and projection parity checks.

Lifecycle

Guarded transition module

Separate task, attempt, workflow, node, agent, human-wait, backend-circuit, watchdog, and self-update lifecycles.

Planning

Versioned roadmap module

Single parser and interface, typed mutations, retained completed/superseded history, local repair, and explicit invalidation.

Workflow

Template, compiler, and runner modules

First encode existing lanes exactly; then conditionally add agent, adapter, check, human, decision, wait, and join nodes.

Project setup

Project profile and synthesis module

init produces deterministic facts; the setup agent proposes judgment-dependent workflow policy for approval.

Code intelligence

Repository graph module

Derived main snapshot, worktree overlays, freshness/confidence, bounded queries, affected areas, and compact context manifests.

Verification

Validation evidence module

Records why a check was valid, marks affected results stale, and initially prefers redundant testing over unsafe reuse.

Scheduling

Explainable priority module

Ranks ready tasks using criticality, backend state, conflicts, risk, capacity, and measured history—without HEFT first.

Governance

Executor interception module

Before dispatch, before effect, after effect, and before completion hooks around Maestro-controlled operations—not assumed backend shell hooks.

04

Foundation-first delivery waves

Each wave creates independently observable leverage. Adaptive workflow generation arrives only after the runner can explain and safely recover its own state.

0

Baseline the real system

Run a second-project initialization and at least one real LLM implementation task. Capture exploration, handoff, recovery, gate, conflict, and human-intervention baselines.

Outcome: evidence for deciding whether later graph features pay for themselves.
1

Control-plane foundation

Add typed events and lifecycle transition checks in shadow mode; compare new projections with existing state.json behavior.

Outcome: explainable state without changing live scheduling.
2

Roadmap deepening

Unify roadmap readers, validate the graph, version changes, and route Maestro-authored changes through typed mutations.

Outcome: safe dynamic planning and invalidation semantics.
3

Compatibility workflow graphs

Express today’s implementer, script, async, manual, resumable, review, merge, and graduation lanes as explicit workflows with behavior parity.

Outcome: the orchestration loop delegates to a deep workflow runner.
4

Project workflow synthesis

Extend setup with a deterministic project profile and a reviewed reusable workflow proposal. Compile the smallest workflow per task.

Outcome: both research approaches are active together.
5

Repository graph and context benchmark

Index main plus isolated worktree deltas. Give agents bounded manifests first and measure whether they replace exploration rather than add to it.

Outcome: verified context savings or a clear rejection result.
6

Validation and roadmap invalidation

Fingerprint evidence, compute affected checks, and invalidate downstream assumptions conservatively. Do not skip established gates until recall is proven.

Outcome: prior engineering evidence survives safe changes.
7

Explainable scheduling and adaptive nodes

Use real duration, quota, source-overlap, and failure data to prioritize the ready frontier and justify optional specialized workflow nodes.

Outcome: more verified work per quota and less parallel rework.
8

External bake-offs only after native evidence

Benchmark Temporal/DBOS, deeper code graphs, advanced schedulers, or reviewer agents against the native modules.

Outcome: dependencies are adopted only when net reliability or efficiency improves.
05

Architecture guardrails

Keep load-bearing Maestro behavior

  • Project-agnostic core and project-owned quality adapters.
  • Claude and Codex as capability-driven backends.
  • Git worktrees as the durable coding artifact.
  • Checkpoint handoffs instead of context compaction.
  • Human gates for risk, uncertainty, and self-modification.
  • Self-update only at safe task boundaries.

Explicitly reject for this integration

  • A universal graph for roadmap, code, execution, and memory.
  • A LangGraph rewrite or generic graph-rewriting language.
  • Neo4j/Memgraph as a baseline dependency.
  • LLM-generated GraphRAG as the source-code truth.
  • Always-on Joern or default debate-agent chains.
  • Claims of exact per-tool recovery from opaque CLI agents.
Safety prerequisite: the prepared but unimplemented filesystem-confinement design must be resolved before a generated workflow is allowed to claim that implementer nodes are physically sandboxed.

The one policy decision still open

When does a synthesized project workflow become active?

Recommended: every generated or materially revised project workflow remains a proposal until Dan approves it. Later, low-risk automatic revisions can be considered only after versioning, diff visibility, deterministic validation, and rollback are proven.

07

Why the visual rule was missed—and how to remove ambiguity

The visible instruction said to include a diagram when relationships would be clearer and described delivery behavior whenever a final visual artifact is created. An inline Mermaid diagram satisfied the first clause technically, while the second clause was conditional. It did not explicitly say that every plan must be delivered as a standalone artifact. The agent also over-weighted the brainstorming skill’s in-chat design gate. The result followed a narrow reading, not the intended workflow.

For every request whose primary deliverable is a plan, workflow, architecture, design, comparison, project recap, or multi-stage change proposal, the final deliverable MUST be a standalone visual artifact created with the visual-explainer skill. An inline Markdown/Mermaid diagram does not satisfy this requirement.

Default to one self-contained HTML artifact. Verify it in a browser, then automatically send that artifact to Dan’s private inbox. The chat response should contain only a concise outcome, the artifact link, delivery status, and any decision that blocks the next stage.

Skip the artifact only when Dan explicitly asks for text-only output or when the requested plan is a simple linear task that fits in three or fewer short steps.
