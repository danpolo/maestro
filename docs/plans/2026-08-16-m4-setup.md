# M4 — Setup: `init`, `doctor`, skills

Spec: `docs/DESIGN.md` §10. Process: `docs/EXECUTION.md`'s M4 stage entry and per-stage loop.

## Scope decisions made before the workflow, so agents don't have to guess

- **`maestro/watchdog.py` is out of scope for this stage.** It appears in DESIGN.md §3's package
  layout, but was never scheduled in the M0–M1 Function → Module Mapping, and DESIGN.md §13 still
  lists "exact stall-detection window and the definition of journal progress for the generic
  watchdog" as an *open* item. Building it now would be inventing behaviour with no reference and no
  spec to extract from — out of character for this build. `cli.py`'s `watchdog` subcommand is
  therefore a thin, honestly-labelled stub (prints "not yet implemented", exit code 1) rather than a
  fabricated implementation. `run`/`ctl`/`status` wrap real existing modules
  (`orchestrator.main`, `hitl.commands`, `state.read_state`) and are not stubs.
- **"a completed no-op supervised loop"** (EXECUTION.md's M4 Done-when) means: a throwaway project
  scaffolded by `maestro init`, with an **empty roadmap** (zero runnable tasks), on which
  `maestro.orchestrator.main()` completes at least one full poll cycle — reaching the idle/no-launch
  branch with `in_flight` empty — and returns/exits cleanly, without needing a task, a Telegram
  token, or a live backend CLI. The cli.py-building agent must determine `main()`'s actual exit
  shape (does it loop forever, or return after one idle pass with nothing runnable?) by reading it —
  that reading is delegated to the agent, per EXECUTION.md's context-discipline rule that the
  orchestrating session never opens extraction-sized modules itself — and report back the concrete
  mechanism used (env var, iteration cap, natural return, or a bounded-subprocess-and-signal
  approach) so it can be recorded in `docs/PROGRESS.md` precisely, not asserted vaguely.
- **`doctor`'s checklist** (DESIGN.md §10: docs, adapters, model limits, backends, Telegram, unit,
  gate, journal/version health) is built in full, but every check must be unit-testable without a
  network call or a real Telegram bot — mirroring the existing rule that a test reaching
  `api.telegram.org` is a defect. Reachability checks take an injectable HTTP call.
- **`install-skills` never writes to `~/.codex/` in a test.** Both destinations
  (`~/.claude/skills/maestro-setup/`, `~/.codex/prompts/`) must be derived from an overridable home
  directory (env var or parameter), the same pattern `Paths.from_env()` already uses for
  `MAESTRO_REPO`, so tests target a temp dir. Real installs still land in the real locations by
  default — this is a testability seam, not a behaviour change.
- **Add a `maestro` console-script entry point** to `pyproject.toml` (`maestro.cli:main`) — this is
  new build scaffolding, not reference code, so no characterisation constraint applies.

## Scope for the workflow

### Component A — `maestro/adapters.py` (DESIGN.md §4)

- One function per adapter kind is unnecessary; a single `run_adapter(kind: str, project_root: Path,
  payload: dict | None = None, timeout_s: int = 120) -> AdapterResult` that resolves
  `adapters/<kind>` under the project root, runs it with the payload as JSON on stdin, parses JSON
  from stdout, and returns a typed result. `kind` is one of `test | eval | smoke | deploy |
  healthcheck | latency` (DESIGN.md §4 table).
- Missing adapter (file absent or not executable) is **not an error** for the optional ones
  (`eval, smoke, deploy, healthcheck, latency` — D8's "absence is journaled as `verdict=unevaluated`,
  never hidden") but **is** an error for `test`, the only required adapter. Encode this as an
  `AdapterResult.status` of `ok | absent | timeout | bad_output | nonzero_exit`, never a raised
  exception for the expected "missing optional adapter" case.
- Non-JSON or malformed stdout → `bad_output`, with the raw tail captured for `doctor` to show.
- `tests/test_adapters.py`: exercise all five status outcomes against small scratch scripts written
  by the test itself (executable temp files) — no dependency on any real project.

### Component B — `maestro/templates/`

Static content the `init` scaffolder copies/renders. Per DESIGN.md §10's *Scaffolds* bullet and §5's
`project.yaml` example (copy that example near-verbatim as the template, with `{{ project_name }}`
/ `{{ repo_path }}`-style placeholders `init` fills from what it derives):

- `templates/project.yaml.tmpl` — DESIGN.md §5's example, placeholders for `project.name`,
  `project.repo_path`, `project.main_branch`.
- `templates/adapters/test` — the only required adapter stub, executable, a clearly-commented
  placeholder (e.g. runs `pytest` if a `tests/` dir exists, else prints a TODO and exits 1) so a
  fresh project is never silently ungated.
- `templates/adapters/{eval,smoke,deploy,healthcheck,latency}` — executable stubs that emit the
  adapter's documented "not implemented" JSON shape from DESIGN.md §4's table (e.g. eval's stub
  returns `{"metrics": {}, "baseline": {}, "deltas": {}, "verdict": "unevaluated", "token_free":
  true, "elapsed_s": 0}` — matching D8) and exit 0, since "absent" already covers the *missing* file
  case; these stubs cover the *present-but-not-yet-wired* case the same honest way.
- `templates/operating_preamble.md` — generic safety rules + a `{{ deny_list }}` placeholder,
  informed by DESIGN.md §4 and §7 (mentions the SWITCH sentinel checkpoint-and-exit contract, since
  that's a rule implementers must actually follow, not just orchestrator-side).
- `templates/profiles/` — one file per role (`orchestrator.md`, `implementer.md`, `judge.md`) — short
  role-scoped instructions, informed by `project.yaml`'s `roles:` block shape.
- `templates/docs/ROADMAP.md`, `templates/docs/PROJECT.md` — minimal machine-readable-roadmap and
  project-doc skeletons matching what `maestro.docs.roadmap.parse_runnable_tasks` /
  `parse_prep_tasks` actually parse (read `maestro/docs/roadmap.py` to match its real expected
  shape, don't invent a format that then fails to parse — this is the one place in this component
  where reading an extracted module is required and expected).
- `templates/pre-commit` — the consistency hook DESIGN.md §10 mentions, calling
  `maestro doctor --pre-commit` (a fast subset) or a placeholder if that's overreach — agent's call,
  document the choice.
- `templates/systemd/maestro-watchdog.service.tmpl` and `templates/launch.sh.tmpl` — per DESIGN.md
  §10's *Systemd and tmux* subsection: `ExecStart` wraps a launcher script that does
  `tmux new-session -d -s <project>-watchdog`, `Type=simple`, `Restart=on-failure`. Since
  `watchdog.py` doesn't exist yet (see scope decision above), the launcher's tmux command should run
  whatever `run`/`ctl` wraps today and say so in a comment — do not invent a call to a module that
  doesn't exist.
- `tests/test_templates.py`: every `.yaml`/`.yml` template parses; every file under `templates/adapters/`
  and `templates/systemd/`/launcher is executable; `ROADMAP.md`/`PROJECT.md` skeletons round-trip
  through the real `maestro.docs.roadmap` parser with zero runnable tasks (this doubles as evidence
  for the "empty roadmap" no-op-loop scope decision above).

### Component C — the setup skill (D6), both formats

- `maestro/skills/claude/SKILL.md` — Claude Code skill format (frontmatter `name`/`description`,
  markdown body). Content per DESIGN.md §10's *The setup skill* paragraph: interviews for what good
  looks like, what's risky, the deny-list, first roadmap tasks, the upcoming-work glossary; then
  calls `init` with the answers; also covers converting an existing project's prose docs into the
  roadmap format.
- `maestro/skills/codex/maestro-setup.md` — same content, Codex prompt format (no YAML frontmatter;
  follow whatever convention `~/.codex/prompts/*.md` already uses on this machine — check one
  existing file there for shape, read-only).
- `tests/test_skills.py` — both files exist, are non-empty, and (for the Claude one) frontmatter
  parses as valid YAML with required keys.

### Component D — `maestro/cli.py` (depends on A, B, C existing — runs after them)

- `maestro init [path]` — idempotent per DESIGN.md §10: derives git root/remote/main branch/test
  command/package manager from the target repo; writes the Component B templates rendered with
  derived values; **anything that already exists is written as `.new` beside the original with a
  diff shown, never clobbered** (the literal DESIGN.md §10 rule — implement this exactly, it's also
  most of "re-running `init` is provably non-destructive"). Prompts for the Telegram token only via
  `scripts/telegram_creds.py` (never reads the token itself — subprocess out, per the secret-handling
  rule); if the token file is absent, skip Telegram setup and continue (matches EXECUTION.md's M4
  "blocked: no credentials" allowance for the *build's own* acceptance run, but `init` itself should
  behave the same way for any future real project missing a token — this isn't scoped to the build).
  Ends with a dry-run `maestro status` and the no-op supervised loop check (component D's own
  research finding above) before reporting success.
- `maestro doctor` — the checklist from DESIGN.md §10, each check a small function returning
  `(ok: bool, detail: str)`: docs present & parseable (via `maestro.docs.roadmap`), adapters
  executable & contract-conforming (via component A's `run_adapter` in a dry mode or a
  `--check`-only path), model limits resolving (via `maestro.limits.resolve_all`), configured
  backends installed and models valid (via `maestro.backends.registry`), Telegram reachable
  (injectable HTTP call, never real in tests), systemd unit installed, gate present (nags, doesn't
  fail, when `gate.chain == ["test"]` only — D8), journal/version health (via `maestro.state` /
  `maestro.selfupdate`). Exit code reflects worst severity; each check prints one line.
- `maestro status` / `maestro run` / `maestro ctl` — thin wrappers: `status` reads and pretty-prints
  `state.json` via `maestro.state`; `run` invokes `maestro.orchestrator.main()` in the target repo
  (setting `MAESTRO_REPO`); `ctl` dispatches to `maestro.hitl.commands`' existing control-command
  handling. `watchdog` is the honest stub described above.
- `maestro install-skills` — copies Component C's two files to the (overridable) Claude/Codex skill
  directories, per DESIGN.md §10's install-skills mapping. **The Codex destination is still governed
  by the operator's delegate-to-agent rule for this *build session* editing the real
  `~/.codex/`** — the acceptance test must point `install-skills` at a temp `$HOME`, never the real
  one, so this workflow's own run never touches `~/.codex/` directly. Real end users running the
  installed `maestro` tool later is a different actor and is exactly what DESIGN.md §10 asks for.
- `pyproject.toml`: add `[project.scripts] maestro = "maestro.cli:main"`.
- `tests/test_cli.py`: `init` on a scratch repo, re-run non-destructively (asserts `.new` files
  appear, originals untouched, diff shown), `doctor` against both a healthy and a deliberately broken
  scratch project, `install-skills` against a temp `$HOME`. The no-op supervised loop mechanism is
  exercised here too, with the concrete approach documented inline.

## Definition of done

Run these myself after the workflow, in this order, recording every number in `docs/PROGRESS.md`:

1. `python3 -m pytest` — full suite, zero skipped, zero failed.
2. `tests/test_adapters.py`, `tests/test_templates.py`, `tests/test_skills.py`, `tests/test_cli.py`
   individually, pass counts recorded.
3. **The literal EXECUTION.md M4 Done-when, run for real on a throwaway `/tmp` project**, never on a
   real one: `git init` a fresh `/tmp/maestro-m4-accept-<random>` repo, run `maestro init` against
   it, confirm the scaffolding lands, run the no-op supervised loop per the recorded mechanism and
   confirm it completes with zero tasks launched, re-run `maestro init` and confirm nothing already
   present was clobbered (only `.new` files appear beside anything that pre-existed — for a truly
   fresh repo this may mean re-running after hand-editing one scaffolded file first, to prove the
   non-destructive path actually triggers).
4. AbuAliArchive read-only check: HEAD, `git status --porcelain`, `.orchestrator/state.json`
   size/mtime, `.orchestrator/HALT` presence — must match the baseline in `docs/PROGRESS.md` exactly.
   Nothing in this stage should touch it (no component reads or writes anything under
   `/home/dan/projects/AbuAliArchive`) but the invariant says check every stage regardless.
